# #57 评估：课表取数「HTTP 直取 JSON 优先、HTML 回退」

- 关联：issue #57（提议）、#53（首次 PARSE_EMPTY）、#54（静默失败）
- 结论：**v0.9.2 不直接大改**；先做 1–1.5 人日可行性 POC，通过后再排 4–6 人日进后续版本。

## 1. 现状（先对齐事实）

- 端侧已有一条**页内 JSON 优先**路径：WebView 打开门户后，注入脚本 hook `fetch`/XHR 捕获
  `queryAWeekSchedule` 模板（cardId/years），随后按周拉 JSON，失败再回退抓 `table#timetable` 的 HTML。
  也就是说「JSON 优先 + HTML 回退」在 **WebView 内**已经存在（t176 起）。
- #57 的**增量价值**是：不用打开 WebView、可在后台刷新 —— 由 Dart 侧直接用用户会话请求接口。
- 需要的前置（#57 自己列了）：会话来源、cardId/学期参数、频率与风控、降级可观测。

## 2. 工作量拆解（端侧 1 人估算）

- 会话 Cookie 读取与请求注入：**1–1.5 人日**。
  用 `flutter_inappwebview` 的 CookieManager 取门户域 Cookie，构造 `Cookie` 头给 Dart HTTP；
  Android WebView 与 Windows WebView2 的 Cookie 存储/HttpOnly/SameSite 行为不同，需要分别兜。
- cardId / 学期缓存复用：**0.5 人日**。
  已有 `CampusCaptureCache.rememberTemplate`，可直接复用；冷启动无缓存时仍需回退 WebView 抓一次。
- 周批量拉取 + 并入现有下游：**0.5–1 人日**。
  复用 `ScheduleApiResult` → `importScheduleJson`（Rust 合并），不新造数据结构。
- 双路径选择、退避、诊断标注：**1 人日**。
  诊断必须写清 `path=api|html` 与失败原因；失败要有退避，避免触发风控。
- 真机验证与回归：**1–2 人日**（Android 多机型 + Windows）。

合计：**约 4–6 人日**（仅 Android 可压到 ~4 人日）。

## 3. 风险

- **会话来源不确定**：HttpOnly Cookie 能否从 WebView 取出、两端是否一致，需真机验证；取不到就得回退。
- **风控/上下文敏感**：接口可能校验 Referer/UA/来源页面；样本仅一次成功，非页面上下文请求有被 403/500 的风险。
- **参数易变**：cardId 每人不同、years/weekcount 运行时才知；强依赖缓存与回退。
- **双路径一致性**：两条路径必须都进 `importScheduleJson`，否则会出现两套解析/两套 bug。
- **可观测不足会放大故障**：没有 `path/reason` 诊断时，线上分不清「接口失败」还是「回退也失败」。

## 4. 建议（v0.9.2 的落地口径）

1. **v0.9.2 不做主路径替换**。只做两件收尾：
   - #53：确认「空壳重取 + 解析重试（≤3 次、行数>0 才放行）」在真机首次抓取不再报 PARSE_EMPTY；
   - #54：关键路径静默错误进 `silentErrors` 并在失败详情可见（本 PR 已做）。
2. **先做可行性 POC（1–1.5 人日）**：Android 端用会话 Cookie 直取 1 周，与 HTML 路径结果逐门对比，
   记录成功率/失败码/风控表现；只读、不替换主路径。
3. POC 通过后，再按上面 4–6 人日排期落地双路径；POC 不通过则维持现有「页内 JSON 优先 + HTML 回退」。

理由：收益（摆脱 HTML 改版、后台刷新）真实，但依赖会话/风控这两个**只能在真机验证**的不确定项。
在 v0.9.2 直接换主路径会把「抓早了」问题换成「会话/风控」新问题，风险大于收益。
