## 1. 设计目标与约束

作者在实现时实际遵守的约束（从代码反推，不是猜的）：

| 约束 | 体现 | 后果 |
|---|---|---|
| **零构建**：不要 npm/webpack/vite，双击就能用 | 前端纯 HTML/CSS/JS，无 package.json；CSS 手写了 Tailwind 子集 | 部署极简，但工具类靠人肉维护 |
| **零数据库**：不装 MySQL/SQLite | 三个 JSON 文件当存储（`memory/profile/file_state`）+ 一个课表 JSON | 单人可用，并发即坏 |
| **单进程单用户** | 全局单例、进程内 `epoch`、无鉴权 | 一切安全问题由此派生 |
| **Windows 优先** | `start.bat`（GBK + `chcp 936`）、硬编码 cpolar 路径 | 不可移植 |
| **模型能力外借**：不自己做检索/RAG | 课表塞进提示词、文档丢给 qwen-long、图片丢给视觉模型 | 开发快，但 token 贵、不可控 |
| **迭代驱动**：遇到什么错就补什么规则 | 提示词里有"历史对话曾把周三下午三四节错算，以本规则为准"这类补丁 | 规则真实有效，但会无限膨胀 |

```

│  main.py(106)          应用装配 + 13 个端点 + /static 挂载          │

    ▼          ▼          ▼              ▼
 memory.json profile.json file_state.json schedule_time.json
  [{role,    {4 自动字段  {file_id,       [{课程名,星期,节,
   content}]  +5 死字段}   name,size,      开始节,结束节,周次,

    │
```

**一句话概括这套架构**：一个"全局唯一的大脑"（记忆/画像/文档状态）住在单进程里，对外裸露在公网隧道上，用同步阻塞的方式调用三个云端模型。

## 3. 技术选型与代价

| 层 | 选择 | 理由（作者意图） | 代价 |
|---|---|---|---|
| Web 框架 | FastAPI | 自带 OpenAPI、异步语法、上手快 | `async def` 里写同步代码反而更危险 |
| 模型 SDK | `openai` 官方包，三家共用 | DeepSeek / DashScope 都兼容 OpenAI 协议，一套代码三处复用 | 端点与模型名靠环境变量，默认值写死（含个人工作空间域名） |
| 搜索 | 自建 `requests.post` 到 `/v1/tools/search` | 想给模型喂实时信息 | 该端点不在 DeepSeek 公开 API 内，失败被吞成"（搜索超时）"→ **大概率长期静默不工作** |
| 存储 | JSON 文件 + `.tmp`/`os.replace` | 零依赖、可人工查看/手改 | 无事务、无并发、无索引、无上限 |
| 前端 | 原生 JS + 手写 Tailwind 子集 | 零构建、无 CDN、可离线 | 无模块化、无 lint、类名与实现靠人工同步 |
| 部署 | uvicorn + CPolar | 学生没有公网 IP | 默认把无鉴权服务暴露到公网 |

## 5. 关键流程

### 5.1 提问主链路（最核心，务必看懂这张图）

```
POST /api/chat {message}
│
├─▶ BackgroundTasks 先登记：update_profile_from_message(message)   ← 响应后执行
│
└─▶ chat_reply(message)                        [同步阻塞，整个事件循环等它]
     1  epoch = memory_epoch()
        memory = load_memory()                 [全量读 JSON]
        file_state = load_file_state()
     2  if 无文档 且 detect_jump_target(message) 命中"成绩/教务/集成"
            └─▶ 直接 return 一段 Markdown 链接        ⚠️ 完全绕过 AI，不写记忆
     3  if 无文档 且 message 含 SEARCH_KEYWORDS（搜/查一下/最新/新闻/天气/大创/比赛）
            └─▶ user_message = web_search(msg) + "\n\n用户问题：" + msg
     4  messages = [
          system: build_system_prompt() + build_schedule_context(),   ← 每轮都全量注入
          (fileid 模式追加) system: 文件说明, system: fileid://xxx,
          * memory[-20:],
          user: user_message
        ]
     5  fileid 模式 ? qwen-long(timeout=120) : deepseek-chat(timeout=30)
     6  memory += {user, user_message}, {assistant, reply}      ⚠️ 存的是"搜索增强后"的文本
     7  if epoch == memory_epoch(): save_memory(memory)          ⚠️ 7 步之间无锁
```

**四个拦截优先级**：跳转 > 搜索 > 文档 > 模型。文档模式下前两个都跳过（作者注释：避免把文档里的"成绩/教务"误判成跳转）。

**并发缺陷**：第 1 步读、第 6 步改、第 7 步写，中间隔着 30~120s 的网络等待。两个请求并发 → 后写的完整覆盖先写的。`epoch` 只防"清空后回魂"这一种情况。

### 5.2 文档上传（qwen-long 模式）

```
POST /api/upload_file (multipart)
  1  content = await file.read()                    ⚠️ 先全量进内存，再判 50MB
  2  len > MAX_UPLOAD_MB  → {"ok": false, "error": ...}
  3  cleanup_temp_files()                           ⚠️ 死逻辑：temp/ 从来没被写入
  4  safe_name = re.sub([^\w.\-()\u4e00-\u9fa5], "_", basename(filename))
  5  DashScope files.create(purpose="file-extract") → file_id
  6  轮询 files.retrieve 至 status == "processed"，最多 15 次 × sleep(1)  ⚠️ 同步 sleep
  7  save_file_state({file_id, name, size, uploaded_at})   ⚠️ 只保留最新一份，远端旧文件不删
  8  if question 非空 → 立刻用 qwen-long 回答（前端从不传 question）
```

进入文档模式后，**所有**后续 `POST /api/chat` 都改走 qwen-long（`file_active` 判定），直到 `/api/upload_file/clear`。

### 5.3 识图

```
POST /api/vision (multipart)
  → base64 → data:{mime};base64,... → 视觉模型
  system = build_system_prompt()   ⚠️ 把用户画像一起发给视觉模型
  timeout = 60s，无大小限制，失败返回 "识图失败：{e}"（HTTP 200）
```

### 5.4 「新对话」——epoch 机制（本项目的亮点之一）

```
POST /api/clear
  clear_memory():  _memory_epoch += 1;  写空列表
  → 在途的 chat_reply 结束时 epoch 不一致 → 丢弃结果，不写回记忆
```
它解决的是"我点了新对话，但上一条回答 30 秒后才返回，把旧上下文写回去了"。**设计意图是对的**，但只覆盖了单进程、单一场景。多 worker 部署会失效（每个进程独立计数）。

### 5.5 课表数据的诞生（离线）

```
schedule.html（教务导出）
  → parse_schedule_time.py
      找 table#timetable、找"星期"表头
      行首 th 的"第N节" → row_period（fallback）
      每个 td 取 div.kbcontent（只取完整版，避免简版重复）→ 按 ------ 切块
      每块按 <font title="教师|周次(节次)|教室"> 抽字段，无 title 的 font = 课程名
      "4-15(周)" / "1-5,7-9(周)" / "1-16单周" → 周次列表
      "01-02节" → (开始节, 结束节)
      按 (课程名,星期,周次,节次,教室,教师) 去重
  → schedule_time.json
运行时：读 JSON → 判当前周 → 拼成 Markdown 文本 → 注入 system prompt
```

## 6. 数据设计

### 6.1 `memory.json`（聊天记忆）

```json
[{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]
```
| 特性 | 现状 |
|---|---|
| 结构 | 扁平数组，**无 session 概念** |
| 增长 | 只增不减（prompt 取 `[-20:]`，但**文件全量保存**） |
| 写入 | `.tmp` + `os.replace`（原子）+ `RLock`（**仅进程内**） |
| 内容 | ⚠️ user 侧存的是"搜索结果 + 用户问题"的拼接文本 |

### 6.2 `profile.json`（长期画像）

```json
{
  "name": "", "school": "", "major": "", "preferences": "", "schedule_notes": "",
  "student_union_role": "学生会文艺部部长",
  "class_role": "班长",
  "current_activities": ["筹备迎新晚会"],
  "other_facts": ["准备考研"]
}
```
| 字段组 | 谁写入 | 现状 |
|---|---|---|
| 前 5 个（name/school/major/preferences/schedule_notes） | **无人写**（`merge_profile` 只处理后 4 个，也没有手动编辑接口） | ⚠️ 永远为空，但前端展示了它们 |
| 后 4 个 | 模型抽取 + `merge_profile` | 字符串直接覆盖；列表去重后截断 12 条 |
| 清空 | `reset_profile` 只弹掉后 4 个 | 与前端按钮文案"清空自动记忆"一致 ✅ |

### 6.3 `file_state.json`（文档模式状态）

```json
{"file_id": "file-xxx", "name": "培养方案.pdf", "size": 123456, "uploaded_at": "2026-10-31 17:52:40"}
```
单对象，**只保留一份**；无 user、无过期时间、无远端回收。

### 6.4 `schedule_time.json`（课表，由离线脚本产出）

```json
[{
  "课程名": "高等数学A", "星期": "星期一",
  "节次": "01-02节", "节": "第1-2节", "开始节": 1, "结束节": 2,
  "周次": "1-16(周)", "周次列表": [1,2,3],
  "开始周": 1, "结束周": 16,
  "教室": "东校区 1 教 305", "教师": "张老师"
}]
```
消费侧字段：`课程名 / 星期 / 节 / 开始节 / 周次列表 / 教室 / 教师`。`开始节` 必须是**整数**，消费端有 `int()` 强转（脏数据会直接抛异常并炸掉整轮对话）。

### 6.5 `schedule.json`（遗留）

`parse_schedule.py` 产出的 `班级/课程编号/课程名/教师/课程性质` **没有周次节次**，与消费端完全不兼容，且脚本在 `import` 时就执行读盘。→ 删。

### 6.6 数据设计的总缺陷

| 缺陷 | 后果 | 目标设计 |
|---|---|---|
| 四个文件都是"全局唯一" | 多人使用必然串号 | 按 `user_id` 分区（SQLite） |
| 无 schema 版本、无迁移 | 改字段后旧文件静默回默认值 | 迁移脚本 + `version` 字段 |
| 无上限、无 TTL | 文件无限增长、全量读写 | 按会话分表 + 保留策略 |
| 读改写无跨请求锁 | 并发丢消息 | 事务（`BEGIN IMMEDIATE` / 单写队列） |
| 明文存储 | 画像/记忆可被直接读取 | 落盘加密或至少权限收紧 + 脱敏日志 |

## 7. 提示词设计（这是"他的想法"里最有价值的部分）

`build_system_prompt()`（`memory_service.py:90-108`）+ `build_schedule_context()`（`campus_api.py` 汇总）拼成一条 system message，结构固定为七段：

| # | 段落 | 作用 | 举例 |
|---|---|---|---|
| 1 | 角色 | 定身份与语气 | "你是「云农之窗」，专为云南农大学生打造的智能校园助理。回答要简洁高效。" |
| 2 | **反称呼规则** | 治"某某同学你好"的油腻感 | "除非用户明确要求，否则绝对不要带上用户的名字" |
| 3 | 画像 | 让回答贴合身份 | 专业、学生会职务、班级职务、正在做的事、其他长期信息 |
| 4 | 时间锚点 | 时间问题必须有基准 | 当前时间 + 第几周 + 学期起点 |
| 5 | **节次换算规则** | 治"下午第 3 节到底是第几节" | "下午第 N 节 = 全天第 N+5 节"，并附正反例 + "不要反问用户" |
| 6 | **课表使用规则** | 治幻觉与编造空教室 | 只根据给定数据回答、没课就说没课、单双周判定 |
| 7 | 课表数据 | 结构化上下文 | 当前周课程列表 |
| 8 | 收尾约束 | 防罗列、防臆测 | "不要无端罗列或反复提及，也不要臆测未提供的信息" |

三个值得保留的设计：

1. **把"用户口语"和"系统编号"的映射写进提示词，而不是写进代码**——因为模型是唯一需要理解这句话的地方，映射规则放这里最有效；
2. **规则带"考古注释"**："历史对话里曾把'周三下午三四节'错算成第 3-4 节，那是错误理解，以本规则为准"——用模型自己的失败案例纠偏，比抽象规则更管用；
3. **负向指令多于正向指令**（不要叫人名字、不要反问、不要罗列、不要臆测）——说明作者是被真实体验逼出来的。

代价：
- 每轮**全量**注入课表（课表越大 token 越贵），且与问题无关时也注入；
- 规则只增不减，提示词会持续膨胀；
- 所有规则都是"软约束"，没有结构化输出（JSON）+ 代码校验兜底。

**重构建议**：把课表从"塞提示词"改成 **function calling / tool**（`get_courses(weekday, week)`），规则压缩成 15 行，时间/周次用代码算好再注入。

## 8. 前端设计

### 8.1 结构

`index.html` 是一个 HTML 里跑三种界面状态，靠 `.chat-area.is-empty` 切换：

```
hero 态（无对话）          会话态（有对话）
├ 标题 + 副标题            ├ 消息流（role=log）
├ 快捷提问 chips ×4        ├ 打字中指示器
└ 大 logo                  └ 输入区（固定底部）
侧栏：品牌 / 6 个校园直达 / 新对话 / 记忆 / 主题 / 折叠
弹窗：记忆面板（9 个字段分组 + 删除 + 清空自动记忆）
```

### 8.2 渲染策略

- `addMsg(role, text)`：先 `escapeHtml` → 再用 `hasMarkdown()` 启发式（含 `|` / `- `/`](` 等）决定走 Markdown 还是纯文本；
- `renderMarkdown` 是 63 行**手写状态机**（代码块 / 标题 / 列表 / 表格 / 引用 / 链接），不是第三方库；
- AI 气泡有 `copy` 按钮（移动端常显），气泡进入用**微笑脸动画**；
- 非 Markdown 的短文本走 `typeWriter`（14ms/字 + 每字滚底）——**这就是"假流式"**。

### 8.3 手写 Tailwind 子集（值得单独说）

`style.css` 里有一个"Utility layer"，用 `[class~="hover:bg-blue-50"]`、`:is(.group:hover) [class~="group-hover:text-white"]` 这类属性选择器**等价实现**了 Tailwind 的变体语法。

- 实测覆盖：HTML + JS 里用到的 **187 个 class token，0 个无实现**（我做了程序化 diff）。工程质量其实比看起来高；
- 代价：类名是"数据"不是"API"，拼错任意一个字符就静默失效；新增组件要同步改 CSS；没有 purge，1056 行里必然有僵尸规则。

### 8.4 值得保留的交互细节

| 细节 | 位置 | 为什么好 |
|---|---|---|
| `isComposing` 判 IME | `app.js` 回车处理 | 中文输入法选词时不误发 |
| `activeRequest !== controller` 代际判断 | 新对话打断旧请求 | 避免旧响应污染新会话 |
| `prefers-reduced-motion` 全量降级 | `style.css` | 动效不折磨人 |
| `safe-area` + `dvh` + `viewport-fit=cover` | `style.css` / `index.html` | 刘海屏/地址栏伸缩不塌 |
| 零 CDN、图标全内联 SVG、系统字体栈 | 全站 | 无供应链风险、无 FOUT |
| 聚焦环 + `sr-only` + `aria-expanded` + Esc | 全站 | 键盘可达 |

### 8.5 前端的结构性问题

| 问题 | 说明 |
|---|---|
| 无模块化 | 697 行单文件、25 个全局函数、21 个全局 DOM 常量 |
| 三份同构上传/发送代码 | `send` / `uploadImage` / `uploadDoc` 各自写一遍 busy→fetch→finally |
| 只有 1 处检查 `res.ok` | 10 次 fetch 里 9 次直接 `res.json()`，后端 422/500 时表现为"（无回复）" |
| 0 处超时 | 无 `AbortSignal.timeout`，`busy` 会永久封死输入 |
| 顶层 `localStorage` 无保护 | 隐私模式下一抛错，整个 `app.js` 中断 → 白屏 |
| 手写 Markdown 的转义不全 | 不转义引号 → `href` 属性可逃逸 |

## 10. 设计缺陷 → 重构方案（对照表）

| # | 现状设计 | 会怎么坏 | 目标设计 | 迁移动作 |
|---|---|---|---|---|
| D1 | 记忆/画像/文档状态为进程级单例 | 第二个人一开口就串号；分享即泄露 | 引入 `user_id`/`session_id`，存储按用户分区 | 新建 `users`/`sessions` 表；所有读写带 `user_id` |
| D2 | 全端点无鉴权，`/docs` 默认开 | 任何人可读画像、清库、烧额度 | 中间件校验 Bearer/口令；生产关 `/docs` | 加 `core/auth.py` + `Depends` |
| D3 | `async def` 里跑同步阻塞 | 一人提问整站冻结（含静态资源） | 同步路由改 `def`（线程池）或全链路异步 | 路由改 `def` + `httpx`；先改 `/api/chat` |
| D4 | 非流式 + 前端假打字 | 首字延迟 = 全量时间 | SSE 流式，前端增量渲染 | 新增 `/api/chat/stream`；保留旧接口兼容 |
| D5 | 读改写无跨请求锁 | 并发丢消息 | 事务 / 单写队列；或直接 SQLite | SQLite WAL + `BEGIN IMMEDIATE` |
| D6 | JSON 无 schema/无版本/无上限 | 改字段即静默丢数据；文件无限长 | SQLite + 迁移脚本 + 保留策略 | 写迁移器读旧 JSON 入库 |
| D7 | 课表全量塞提示词 | token 贵、规则膨胀、无关也注入 | 改为工具调用 `get_courses(weekday, week)` | 定义工具 + 代码侧查询 |
| D8 | 关键词子串拦截跳转 | "教务密码忘了"只会给链接 | 意图分类 + 跳转作为建议 | 关键词表外置 + 模型兜底分类 |
| D9 | 画像抽取由高频词触发 | 几乎每条消息多花一次钱 | 异步队列 + 去重 + 节流 + 可手动编辑 | `profile_jobs` 表 + 手动编辑接口 |
| D10 | 错误一律 200 + 中文 | 调用方无法程序化识别；泄露 `str(e)` | 统一错误信封 + 正确状态码 | `core/errors.py` + 前端按 `code` 分支 |
| D11 | 前端无 `res.ok`/无超时/无取消 | 卡死无出路 | 统一 `request()` 封装（超时+重试+取消） | 抽 `api.js` |
| D12 | `escapeHtml` 不转义引号 + 无 CSP | 属性注入 | 转义 `"'` + URL 白名单 + CSP | 改 `escapeHtml` + 加响应头 |
| D13 | 学期起点硬编码 | 跨学期课表静默失效 | `terms` 表 + 多学期归档 | 建表 + 从配置读取 |
| D14 | 部署依赖硬编码路径与 `--reload` | 不可移植、不安全 | 环境变量/配置文件 + 生产模式 + 反代 TLS | 重写启动脚本 + Dockerfile |
| D15 | 无依赖声明 | 换机必挂（实测缺 `openai`/`bs4`） | `requirements.txt`（锁版本）+ `.env.example` + README | 直接补 |

### 11.1 SQLite schema 草案

```sql
CREATE TABLE users    (id TEXT PRIMARY KEY, created_at TEXT NOT NULL);
CREATE TABLE sessions (id TEXT PRIMARY KEY, user_id TEXT NOT NULL,
                       title TEXT, created_at TEXT, updated_at TEXT);
CREATE TABLE messages (id INTEGER PRIMARY KEY AUTOINCREMENT, session_id TEXT NOT NULL,
                       role TEXT NOT NULL, content TEXT NOT NULL,
                       tokens INTEGER, created_at TEXT NOT NULL);
CREATE TABLE profiles (user_id TEXT NOT NULL, field TEXT NOT NULL, value TEXT NOT NULL,
                       source TEXT, updated_at TEXT NOT NULL,
                       PRIMARY KEY (user_id, field));
CREATE TABLE files    (id TEXT PRIMARY KEY, user_id TEXT NOT NULL,
                       provider TEXT, provider_file_id TEXT, name TEXT, size INTEGER,
                       status TEXT, created_at TEXT, expires_at TEXT);
CREATE TABLE terms    (term TEXT PRIMARY KEY, starts_on TEXT NOT NULL, ends_on TEXT);
CREATE TABLE courses  (id INTEGER PRIMARY KEY AUTOINCREMENT, user_id TEXT NOT NULL,
                       term TEXT NOT NULL, name TEXT NOT NULL, weekday INTEGER NOT NULL,
                       start_period INTEGER NOT NULL, end_period INTEGER NOT NULL,
                       weeks TEXT NOT NULL, room TEXT, teacher TEXT);
CREATE INDEX ix_messages_session ON messages(session_id, id);
CREATE INDEX ix_courses_user_term ON courses(user_id, term);
```

### 11.2 三个关键决策

1. **鉴权先做，功能后加**：单用户也用令牌，是为了让"分享"不再是事故；
2. **课表从提示词变成工具**：一次性砍掉大段上下文与规则，顺带解决"跨学期失效"（工具内部按 `terms` 判周）；
3. **先流式再优化**：SSE 是体验收益/成本比最高的一刀，且能顺带把"同步阻塞"彻底暴露出来（流式下你无法再在 async 里 sleep）。
