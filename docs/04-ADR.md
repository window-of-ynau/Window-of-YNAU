# 云农之窗 · 架构决策记录（ADR）

| 项 | 内容 |
|---|---|
| 版本 | v1.0（2026-10-31） |
| 性质 | **架构决策的唯一事实来源**。设计文档只引用本文，不重复结论 |
| 每条格式 | 决策 → 划定的边界 → 越界防范 → 失败模式 → 否决的备选 |

> **为什么重写这一版**：上一版 ADR 是"选型记录"（我们用了 Rust、用了 SSE），不是架构决策。真正的 ADR 要回答三件事：**这条边界划在哪、越界了怎么防、这条边界塌了系统怎么退化**。

## ADR-01 三域划分：端 / 云 / 知识

**决策**：系统只有三个信任域。

| 域 | 有什么 | 绝没有什么 |
|---|---|---|
| 端（A） | 学校 Cookie、用户 API Key、会话正文、记忆、私有文件、日历 | 无"多用户共享"概念 |
| 云（B） | 鉴权、时效授权、Auto Review、代理转发、配额、审计 | **默认无正文、无凭据、无长期存储** |
| 知识（C） | 公共文档、分块、向量、引用元数据 | 无任何用户私有内容 |

**边界**：任何数据只能有一个"家"。跨域时必须回答：谁发起、谁见证、留存多久。

**越界防范**：代码层面按 crate/module 隔离（`core/` 无法 import `server/`）；CI 里加"禁止把 `messages` 写入云端表"的静态检查；日志脱敏中间件统一出口。

**失败模式**：
- 云塌了 → 端仍可用（BYOK 对话、本地记忆、课表、日历全部本地）；
- 端被逆向 → 只泄露**该用户自己**的数据（没有别人的）；
- 知识库被污染 → 只影响回答质量，不影响用户数据。

**否决备选**：单域架构（全上云）——隐私叙述无法成立，商业化尽调过不去。

## ADR-02 云端 = 控制面 + 过路面，不是数据面

**决策**：云端**转发**内容但**不落库**；除账号、用量、知识、审计外，不持久化任何用户内容。

**边界**：`messages` 在云端的存在时间 = 一次请求的生命周期（进内存 → 转发 → 丢弃）。

**越界防范**：
- 禁止为"调试方便"把请求体写进日志（CI 检查 + 日志采样只记长度与 hash）；
- 崩溃转储（crash dump）在容器里关闭或加密；
- 任何"想存一下"的新需求，必须先改本 ADR。

**失败模式**：服务重启丢在途请求 → 客户端重试；不丢用户数据（数据在端上）。

**代价（明说）**：换设备聊天记录不会自动跟着走（见 ADR-10）。

**否决备选**：E2EE 数据面（1.1 可选，见 ADR-10）；明文数据面（合规风险最高）。

## ADR-03 套餐 = 服务端代理 + 时效授权，不发上游 Key

**决策**：
- 套餐用户在客户端只持有**我们签发的有效性令牌**（不透明串，服务端可随时吊销；见 ADR-15），拿不到任何上游 Key；
- 所有套餐流量经我们代理：`客户端 → 我们 → 厂商`；
- **按时间计费，不按 token 记账**；token 只做**抽样成本监控**（1% 采样 + 厂商账单回归）。

**边界**：上游 Key 只存在于服务端环境变量/密钥管理；客户端永远不接触。

**越界防范**：
- 每用户并发 = 1；全局闸门 = 50；单轮输入 ≤ 32K；
- 抽样记账用于异常检测（某用户消耗是均值 20 倍 → 告警 + 临时限流）；
- 令牌不可续期绕过（到期需重新购买）。

**失败模式**：
- 代理挂了 → 套餐用户不可用，**BYOK 用户完全无感**（这是本决策最大收益）；
- 上游 429 → 池化 key 轮转；池空 → 明确 `UPSTREAM_ERROR`，不静默降级。

**否决备选：下发共享上游 Key（曾被提出）**

| 理由 | 为什么否决 |
|---|---|
| "没人会逆向" | Key 进过客户端就必然在运行时是明文；解包 + `strings` 即得，Frida 只是更体面。动机极强（免费白嫖 API），这是低成本高收益攻击 |
| "省掉每次鉴权" | 鉴权是本地签名校验 ≈ 几十微秒，不是瓶颈；真正的成本是 token，而代理只增加一跳 30~60ms |
| "省服务器带宽" | 一次对话约 4KB 上行 + 15KB 下行；1000 人 × 20 轮/天 ≈ 12GB/月，可忽略 |
| **致命项**：共享 Key 撞厂商限流 | 厂商限流按 key/组织算。50 并发 ≈ 24 万 token/分钟，已贴个人 key 上限；一人跑长文档 = 全站 429。代理可做 key 池化，下发则做不到 |
| **致命项**：时间限制 ≠ 用量限制 | 一个用户一小时内可烧穿整月预算，而套餐还没到期；没有实时熔断就只剩账单告警（滞后） |

**保留的例外**：可发"应急 Key"用于我们服务不可用时（离线保障），但 1.0 不做。

## ADR-04 BYOK = 端侧直连，Key 不出端

**决策**：用户自带 Key 时，请求由端侧 Rust 直接发往厂商，**不经过我们**。

**边界**：Key 只存在于 OS 安全存储（Android Keystore / Windows DPAPI）与进程内存；不出端、不进日志、不进崩溃报告。

**越界防范**：`test_provider()` 的网络请求由 Rust 发出，Dart 层拿不到 Key；Key 用完即清零内存。

**失败模式**：Key 失效 → 提示"测试连通性"；无网 → 提示切套餐或稍后重试。

**代价**：BYOK 流量不经云端 → **Auto Review 覆盖不到**（ADR-06 的必然结果），且我们无法为其提供实时熔断。

## ADR-05 工具循环 = 无状态多轮请求（已定：方案 B）

**决策**：不做 WebSocket、不做端侧预取；模型输出 `tool_call` 后，客户端执行工具，再**发起一次新的 HTTP 请求**把工具结果带回。

**边界**：工具执行**永远在端侧**；云端只转发，不理解、不执行、不缓存工具结果。

**必须实现的 4 条硬约束**：

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 并发闸门按 `turn_id` 计，不按 HTTP 请求计 | 否则第 2 轮被自己第 1 轮的闸门挡住 |
| 2 | 最多 4 轮，超限强制收尾 | 防模型自己转圈烧钱 |
| 3 | **append-only**：只追加、不重排、不中途压缩 | 前缀稳定才能命中厂商 prompt cache；中途压缩会让缓存全失效，成本翻倍 |
| 4 | 按 `round` 幂等 | 客户端可安全重试第 N 轮；服务端拒绝重复 round |

**失败模式**：第 3 轮失败 → turn 未完成，客户端可重试该轮；已消耗 token 照常计量（抽样）。

**否决备选**：
- **端侧预取**（发请求前本地查好数据注入）：一轮一次往返、最省 token，但模型无法在生成中途决定要什么数据，复杂问题会答错；
- **WebSocket 双向**：体验最好，但与"云端是控制面"冲突（要维护连接态、断线重放）。

**代价（明说）**：每轮 +1 RTT + 一次鉴权，长任务 3~4 轮。

## ADR-06 Auto Review 只作用于套餐通道

**决策**：两道闸——**同步规则拦截**（毫秒级，可疑即拒）+ **异步模型复核**（事后抽查，命中则吊销并要求整改）。

**边界**：审核只覆盖"经我们转发的请求"。BYOK 直连物理上无法审核。

**越界防范**：规则拦截失败不影响正确请求（白名单放行）；模型复核结果进审计表，不阻塞用户。

**失败模式**：审核服务超时（>300ms）→ **放行 + 记审计**（不牺牲可用性，靠事后追责）。

**否决备选**：同步模型审核（+300ms 延迟，用户体验不可接受）；不审核（商业化后被滥用的成本不可控）。

## ADR-07 端侧胖核心 / 瘦 UI

**决策**：**编排逻辑（agent loop、上下文装配、压缩、工具分发、网关）全部在 Rust**；Flutter 只做渲染与交互。

**边界**：Dart 层不持有业务状态（不存消息列表、不做上下文裁剪），只持有 UI 状态。

**越界防范**：Dart 只通过生成的 FFI 接口访问核心；数据层唯一入口是 `core`。

**失败模式**：Rust panic 不能拖垮 UI 线程（FFI 边界捕获，转成错误返回值）；核心崩溃 → UI 显示可恢复错误，重启后从 SQLite 恢复。

**否决备选**：逻辑放 Dart（跨端复用差、无法与服务端共享类型、加密/解析生态弱）。

> **待你确认的一点**：本文按"Flutter 原生 UI + App 内嵌 WebView（仅校务页）"理解。如果你的意思是**整个 App 就是一个 WebView 壳**（UI 用网页写、Flutter 只做壳），那 ADR-07 与前端技术栈都要改——这个歧义必须消掉。

## ADR-08 存储：端 SQLite / 云 PostgreSQL，云端没有 messages 表

**决策**：端侧 SQLite 存全部隐私数据；云端 PG（+pgvector）只存账号、授权、知识、抽样用量、审计。

**边界**：`messages` / `memory_blobs` / 图片**只存在于端侧**（ADR-02 的直接推论）。

**越界防范**：云端迁移脚本里根本不建这些表；新增云端表必须过本 ADR。

**失败模式**：SQLite 损坏 → 从 `.bak` 与 WAL 恢复；端侧全丢 → 云端只有摘要与日程（可用但贫瘠，这是有意的取舍）。

**否决备选**：MySQL（要另配向量库，多一个组件多一次一致性事故）。

## ADR-09 检索分层：私有 BM25 / 公共向量

**决策**：
- **私有文档**（培养方案、笔记）→ 端侧 **BM25**，不装模型、隐私不上云；
- **公共知识**（论文、规章、清洗网页）→ 云端 pgvector + rerank，回答带引用；
- `< 2 万字` 的文档**直接全文进上下文**，不建索引（比 RAG 更准）；
- 定义 `trait LocalIndex`，向量实现留作 1.1 的可插拔项（`bge-small-zh` int8 ≈ 24MB + ONNX 3~6MB）。

**边界**：私有内容永不进入云端索引；公共知识必须可溯源、可删除。

**越界防范**：入库需审核（`status=approved` 才可检索）；引用缺失即视为编造（回答判失败）。

**失败模式**：知识库不可用 → 跳过 RAG，且**禁止编造引用**；BM25 索引损坏 → 退化为全文直塞。

**否决备选**：全上云（隐私破功）；端侧向量为主（+25~30MB 包体，先量再买）。

## ADR-10 跨端：1.0 备份文件 / 1.1 E2EE，不做明文同步

**决策**：
- **1.0**：端侧导出**加密备份文件**（AES-GCM + Argon2 口令派生），新设备导入去重；
- **1.1**：可选 **E2EE 云备份**（默认关闭），主密钥由恢复码派生，云端只存密文；
- **永不做**：明文云同步会话正文。

**边界**：云端可存"派生数据"（日程、课表、画像、摘要）；**不存凭据、不存正文**。

**越界防范**：`sync_enabled` 默认 false；开启需二次确认并展示"云端能/不能看到什么"。

**失败模式**：恢复码丢失 = 密文永久不可解（必须用巨大字体警告）；导入冲突 → 日程按 `updated_at` 后写胜出，会话按设备独立**不合并**。

**否决备选**：明文云同步（拖库即全泄露，尽调硬伤）；会话合并（语义上做不到，会制造幻觉）。

## ADR-11 身份：自注册为主，校方授权为增强；不存密码、不转授会话

**决策**：
- 1.0 用**自注册账号**（邮箱/邀请码）；
- 校方 **OAuth/CAS** 作为 1.1+ 的增强（拿到可撤销 token 后，抓取退化为降级路径）；
- **不收集学校账号密码**；
- **不做 Session 跨端转授**（不把学校 session 传到云端或另一台设备）。

**边界**：学校凭据（cookie/session）只在产生它的那台设备上存在。

**越界防范**：客户端不提供"输入学校密码"的界面；云端代码里不出现任何"代登录"路径。

**失败模式**：用户换设备 → 需在新设备上重新登录学校系统（但课表/成绩/日程已从云端派生数据恢复）。

**为什么不做 Session 复用**（曾被提出"用 Session ID 伪装学校登录"）：

| 风险 | 后果 |
|---|---|
| 写操作放大 | 教务 session 还能**选课/退课**；凭据泄露 = 别人能动你的选课 |
| 风控互踢 | 单会话/绑 IP 的 CAS，跨网络使用会触发异常登录或踢掉另一台设备 |
| 合规定性 | 第三方代持学生会话通常违反学校 ToS；商业化尽调必问 |

**替代方案（能同样实现"换机不丢"）**：同步**派生数据**（课表/成绩/日程/画像），不传 session。

## ADR-12 服务端形态：模块化单体 + PG 队列，1.0 单实例

**决策**：一个 Rust 二进制，内部模块边界清晰（`auth / proxy / review / quota / knowledge / usage / admin`）；后台任务用 **PG 表当队列**（不引 Redis/Kafka）；1.0 部署**单实例**，并发闸门用进程内信号量。

**边界**：闸门是进程内的 → 多实例会变成 `50 × N`。这是**已知且被接受**的 1.0 限制。

**越界防范**：扩容前必须先把闸门换成分布式实现（PG advisory lock 或 Redis 令牌桶），并把 TODO 写进 release 检查单。

**失败模式**：进程重启 → 在途请求失败（客户端重试），闸门自动复位，无状态残留。

**否决备选**：微服务（1000 在线用不上，运维成本翻倍）；Redis/Kafka（PG 队列足够，少两个组件）。

## ADR-13 三协议 = 手写薄适配 + `shared` 单一契约

**决策**：不用各家官方 SDK，用 `reqwest + serde` 手写 `Completions / Responses / Messages` 三个适配器，输出统一 `Chunk`；契约类型只在 `shared` crate 定义一次，端/云/文档/OpenAPI 全从它生成。

**边界**：协议差异**不得**泄漏到编排层与 UI；新增厂商只能新增适配器，不能改上层。

**越界防范**：契约测试对三协议跑同一组 fixture；`shared` 改动必须同时通过端与云的编译。

**失败模式**：某家改了流式字段 → 适配器报 `UPSTREAM_ERROR`，不影响其他协议。

**否决备选**：直接用官方 SDK（快，但把三家差异带进业务层，且 SDK 体积与依赖不可控）。

## ADR-14 许可与数据权利

**决策**：**AGPL-3.0 + 商业双许可**；用户拥有自己的数据：一键导出、一键删除、云端可查"我们存了什么"。

**边界**：AGPL 约束的是服务端分发；商业客户走商业许可。

**越界防范**：贡献者需签署 CLA（否则无法双许可）；数据删除必须覆盖云端 + 备份轮转周期。

**失败模式**：开源后无法收回 → 因此**核心价值（知识库运营 + 校方合作）与代码分离**，代码开源不等于生意没了。

## ADR-15 令牌用不透明串，不用 JWT

**状态**：已定（2026-10-31）
**决策者**：captain

### 背景

需要"登出立刻失效"和"设备可单独吊销"。JWT 是无状态的，要吊销必须再加黑名单表——等于把复杂度挪了个地方，还多一个签名密钥要轮换。

### 决策

访问令牌 = 64 位十六进制随机串（两个 UUIDv4 拼接），**服务端只存 SHA-256**；刷新令牌同理，**一次一换**。校验 = 查表（命中、未吊销、未过期）。

### 边界

- 令牌明文只在响应体里出现一次，之后任何地方（日志、DB、崩溃转储）都只有哈希；
- 令牌与设备绑定，换设备不共享；
- 学校凭据（Cookie）与本决策无关——那些**只留在端上**（ADR-11）。

### 越界防范

日志中间件禁止打印 `Authorization` 头；DB 里没有明文令牌列可查；`access_tokens.token_hash` 上有唯一索引。

### 失败模式

| 情况 | 行为 |
|---|---|
| 令牌不存在 / 格式错 | 401 `UNAUTHORIZED` |
| 令牌存在但已过期 | 401 `TOKEN_EXPIRED`（客户端据此触发 refresh） |
| 刷新令牌被重复使用 | 401；1.0 简化：不牵连同设备其他会话 |
| 登出 | 当前访问令牌精确吊销 + 该账号刷新令牌全清 |

### 否决的备选

| 备选 | 否决理由 |
|---|---|
| JWT（HS256/EdDSA） | 无状态换"无法吊销"；要吊销就得加黑名单表，反而更复杂；还要管签名密钥轮换 |
| Session Cookie | 原生客户端（Flutter/Windows）没有 Cookie 语义，还得处理 CSRF |

### 代价

每个受保护请求一次索引查询。1000 在线 / 50 并发生成下是每秒几十次点查，可忽略。

### 复审条件

QPS 超过 2000，或需要跨服务共享会话时，再评估 JWT + 短 TTL。

## ADR-16 契约可表达性升级：`tool_calls` 与「一事件多 Chunk」

**状态**：已定
**日期**：2026-10-31
**决策者**：队长（yunong-w2b）拍板；提案与实现：端侧负责人（lead-client）

### 背景

写三协议适配器时撞到两处 P0 缺口（[`docs/design/contract-gaps.md`](design/contract-gaps.md)
C1 / C6）。这两条不是"实现写错了"，而是**内部契约表达不了上游语义**：

1. `ChatMessage` 没有 `tool_calls`：assistant 的工具调用只能塞进 `content`，"边说边调工具"
   与并行多调用都表达不出来，三个适配器各自发明了"`content` 当 arguments 用"的土约定。
2. `parse_event` 一次只能返回一个 `Chunk`：Anthropic 的 `message_delta`（`stop_reason` +
   `usage`）与 Responses 的 `response.completed`（**唯一**终态**且**唯一 usage 来源）必须二选一，
   丢 token 数 = 成本监控失真。

### 决策

1. `ChatMessage` 增加 `tool_calls: Vec<ToolCallRef>`（`id` / `name` / `arguments: serde_json::Value`），
   `content` 回归**纯文本**；`ToolCallRef` 与 `Chunk::ToolCall` **同构但不共用类型**。
2. 删除 `parse_event(...) -> Option<Chunk>`，改为 `parse_events(...) -> Vec<Chunk>`；
   同事件多 Chunk 的顺序固定为 `[.., Usage, Done]`（`Done` 必末且唯一）。
3. `Usage` 语义硬化（不改类型）：`0` = "本事件未携带该字段"，同一 turn 的多个 `Usage`
   按字段取 max 合并。

### 边界

- 这条决策**划定**了：内部契约必须能表达"上游一次说了几件事"，而不是让每个适配器自己
  就地降级；降级点必须写在适配器注释里，不能散落到编排层。
- **绝不能**越过的线：`Chunk` 的字段是**对外 SSE 的 wire 形状**，不能为了"内部类型整洁"
  而改（所以 `ToolCallRef` 不替代 `Chunk::ToolCall`）；`parse_events` 是**内部 API**，
  不是对外 HTTP 契约，端/云各自调用，wire 不受影响。
- 发起与见证：端侧 `protocols` 产出 `Vec<Chunk>`，`gateway` 消费并注入 `Meta`；
  云侧（套餐代理）**复用同一套** `parse_events` 与 `ChunkAssembler` 把上游事件装成 SSE，
  只在内存里过一遍——不落库、不改语义、不另写一份去重逻辑。

### 越界防范

- **契约测试**：三协议各有 fixture 覆盖"文本 + 工具同轮"与"usage + 结束原因同事件"；
  `crates/shared` 的单测守着向后兼容（旧 JSON 没有 `tool_calls` 必须能读）与三条结构校验。
- **编译期**：删掉 `parse_event` 而不是留兼容壳，任何漏改的调用点直接编译失败。
- **文档**：`docs/03` §9.1~9.3 写死顺序不变量与合并口径；`contract-gaps.md` 留缺口清单。
- **发请求前失败**：`ChatRequest::validate` 拦住"非 assistant 带 `tool_calls`"、"空 `id`/`name`"、
  "`role=tool` 缺 `tool_call_id`"，不把这些错误留给上游 400。
- **`[DONE]` 去重**：`[DONE]` 是幂等收尾标记，Completions 在 `finish_reason` 帧之后还会再来一次；
  "`Done` 唯一"由 `shared::stream::ChunkAssembler` 统一保证（首个 `Done` 为准），不能靠丢掉带真实原因的
  `finish_reason`。契约测试 `stream_done_invariant_and_dedup_contract` 把这条写死。

### 失败模式

| 这一侧塌了 | 系统会怎样 | 用户看到什么 |
|---|---|---|
| 适配器忘了把 usage 和 Done 一起返回 | 契约测试失败（fixture 断言 `[Usage, Done]`），合不进去 | 无（CI 阶段拦住） |
| 聚合层把不完整分片当完整 JSON 发出去 | Completions / Responses 原样转发片段，上游报参数非法 | 明确错误提示（而不是"参数是空的"的假成功） |
| Anthropic 的 `tool_use.input` 收到字符串片段 | 降级成 `{}`（Anthropic 硬性要求对象），参数丢失 | 工具报"参数缺失"，模型改口重试 |
| 记账层不做 max 合并 | 只记到 `message_start` 的 input、丢掉 output | token 统计偏低（成本监控失真，非资损） |

### 否决的备选

| 备选 | 否决理由（事实，不是"更复杂"） |
|---|---|
| 保留 `parse_event -> Option<Chunk>` 兼容壳 | 只能二选一，留壳必被误用，C6 等于没改；当时全仓无生产调用方，删除成本为零 |
| assistant 的 arguments 继续塞 `content` | 文本与调用无法共存、并行调用无法表达；三协议各自变通会让契约名存实亡 |
| 让 `Chunk::ToolCall` 直接复用 `ToolCallRef` | `Chunk` 是对外 SSE 的 wire 形状（`{"type":"tool_call",...}`），内部重构不能改对外契约 |
| 一事件一 Chunk，在 gateway 里再解析原始 JSON 补 usage | 协议知识泄漏到 gateway，适配层被拆成两半，各家 JSON 形状要在两处维护 |

### 代价（必须诚实地写出来）

- `parse_events` 从 `Option` 变 `Vec`，调用方要处理"一个事件多个 chunk"，gateway 略复杂。
- `ToolCallRef` 与 `Chunk::ToolCall` 字段重复，靠注释 + 测试防止两边漂移（刻意接受的冗余）。
- "0 = 未携带"要求记账层不能把单事件 usage 当总量，多了一条合并规则要守。
- 删掉 `parse_event` 让下游必须同步改名；W2b 按 t1 → t2/t3 顺序串行，实际没有并行撞车。

### 复审条件

- 上游出现"一个事件多个工具调用 + 分片参数"的形态，或接入第四家协议时；
- 记账精度提高到"按事件逐条对账"（那时需要给 `Usage` 增加来源事件标识）；
- 若某家改为保证 usage 是累计全量（当前 Anthropic 是分片），max 合并口径需要重新论证。

## ADR-17 并行工具调用需要序号：`Chunk::ToolCall.index`

**状态**：已定
**日期**：2026-11-01
**决策者**：队长（yunong-w2b）拍板；提案：端侧负责人（lead-client）；实现：端侧适配器 + 契约层

### 背景

ADR-16 让 assistant 能在一条消息里发起**多个**工具调用（并行调用），但 wire 上的
`Chunk::ToolCall { id, name, arguments }` **没有序号**。问题出在流式分片：

- 三个上游都把工具参数**按事件分片**下发（`choices[].delta.tool_calls[]`、
  `content_block_delta` 的 `input_json_delta`、`response.function_call_arguments.delta`）；
- 分片里只有"片段"，`id`/`name` 往往只在**首片**出现，后续片是纯 JSON 字符串；
- 端侧要拼参数，就必须知道"这一片属于哪个调用"。没有序号时只能按到达顺序猜——
  两个调用交错时会把 A 的参数拼到 B 上，**静默产出错误参数**（最坏的失败模式：
  不是报错，而是拿错参数去执行）。

### 决策

`Chunk::ToolCall` 增加 `index: Option<u32>`：

```rust
ToolCall { id: String, name: String, arguments: serde_json::Value, index: Option<u32> }
```

- `None` 时 **不序列化**（`skip_serializing_if`），旧客户端读到的 wire 与之前**逐字节一致**；
- 三适配器各取自己的序号字段：Completions `choices[].index` 上下文里的
  `tool_calls[].index`、Anthropic `content_block_start.index`（`content_block_delta.index`）、
  Responses `output_index`；
- 只加在 **`Chunk`（wire）** 一侧；请求侧的 `ToolCallRef` 不动（它不需要序号）。

### 边界

- 这条决策**划定**了：并行调用的"归位信息"是**契约的责任**，不是聚合层的私事；
  聚合层可以自由决定怎么缓存分片，但不能要求上游按顺序给。
- **绝不能**越过的线：`index` 只在 `Chunk::ToolCall` 上，不能拿它当"调用顺序"的语义
  （上游的 `index` 是槽位号，可能复用，也可能不连续）；工具结果的相关性仍然只认 `id`。
- 端/云都不因为这条改动多存东西：服务端只是把 `Chunk` 原样转成 SSE。

### 越界防范

- **兼容性测试**：`index` 缺失时反序列化 / 序列化的 wire 与旧版一致（`shared` 单测守着）。
- **三协议 fixture**：每个适配器都有一条"并行双调用"用例，断言两个调用的分片各自归位。
- **文档**：`docs/03` §9 的类型块与 `docs/design/contract-gaps.md` C9 落地位置；
  `Chunk::ToolCall` 的注释写明"`index` 是槽位号，不是顺序"。

### 失败模式

| 这一侧塌了 | 系统会怎样 | 用户看到什么 |
|---|---|---|
| 适配器漏取 `index` | 该调用 `index=None`，聚合层退回"按到达顺序"——交错时参数错位 | 工具报参数非法，模型改口重试（有日志可追） |
| 聚合层把 `index` 当顺序用 | 多调用场景下结果顺序错乱（内容对、顺序错） | 工具执行顺序奇怪，结果仍可用 |
| 上游不给 `index`（自建兼容端点） | 全部 `None`，退化为"一次只跑一个工具"的安全路径 | 并行调用变串行，功能不丢 |

### 否决的备选

| 备选 | 否决理由（事实，不是"更复杂"） |
|---|---|
| 让端侧按 `id` 自己归位 | 参数分片里**没有 `id`**（只有首片有），拿不到就无法归位 |
| 用 `Chunk::ToolCall` 的到达顺序隐式编号 | 并行调用会交错到达，顺序≠槽位；错位是**静默**的错误参数 |
| 在内部另开一条"分片通道"类型 | 等于对外 SSE 出现第二套工具调用形状，客户端要维护两条解析路径 |
| 强制上游"一次只返回一个工具调用" | 厂商没有这个开关；而且并行调用本身是省延迟的主要收益 |

### 代价（必须诚实地写出来）

- `Chunk::ToolCall` 多一个可选字段，三适配器都要多取一次序号；`shared` 多一条兼容性测试。
- `index: Option<u32>` 的"`None` 不序列化"约定，要求以后**任何**对 `Chunk` 的扩展都遵守
  "可选字段缺省不序列化"，否则会悄悄破坏 wire 兼容。
- 它只解决"归位"，不解决"跨事件聚合"（缺口 C7 仍挂着）：聚合状态依然在 gateway。

### 复审条件

- 上游开始在同一次调用里跨多个 `index` 复用槽位（当前 Anthropic 会复用，需观察是否跨调用）；
- 引入第四家协议且其分片不带任何槽位信息时（那时要在适配器里做"单调用假设"并降级）；
- 端侧开始需要"调用顺序"语义时——那是另一个字段（`order`），不能复用 `index`。

## ADR-18 校务会话存放在 WebView 自身 profile，不进端侧数据库

**状态**：已定（W6）

### 背景

W6 要求"重启免二次登录"，而 ADR-02 / ADR-11 要求凭据不出端、不入库、不进日志。
两种做法：① 自己抓 `Set-Cookie` 存 keystore 再注入；② 交给平台 WebView 的会话存储。

### 决策

采用 ②。Windows 用 WebView2 user data folder（`%LOCALAPPDATA%\yunong\webview\`），
Android 用系统 CookieManager（应用私有目录）。端侧代码**从不读取** Cookie 值。

### 边界

- Cookie 不进 SQLite / JSON / 日志 / 上传；
- 端侧只读页面可见的业务元素（课表表头、学号栏）判定登录态；
- 上报给端的路径去掉 query 与 fragment（CAS 的 `ticket` 属凭据）。

### 越界防范

端侧从不调用 `document.cookie`；注入脚本白名单只收 `type/html/url/message`；
会话介质由 OS 账户与应用沙箱隔离，不经过我们的代码。

### 失败模式

| 情况 | 行为 |
|---|---|
| 会话失效 | CAS 跳到登录页，探针报 `login_form`，用户登录后自动继续 |
| 用户清理应用数据 | 会话丢失，需重新登录一次（可接受） |
| 页面结构改版 | 探针 `no_signal`，抓取 `HTML_CHANGED`，提示反馈且不清库 |

### 否决的备选

| 备选 | 否决理由 |
|---|---|
| 自己抓 `Set-Cookie` 存 keystore 再注入 | 需自行处理 Domain/Path/SameSite/HttpOnly 与 CAS 多域跳转，出错面大，且容易把凭据落进我们自己的存储 |
| 把 Cookie 存进 SQLite 便于"跨平台一致" | 直接违反 ADR-02/ADR-11 的凭据边界 |

### 代价

卸载或清理应用数据会丢会话；Windows 与 Android 的存储位置不同，需在文档写清（见 docs/03 §8.3）。

### 复审条件

若需要跨设备共享会话，或平台 WebView 无法满足 CAS 的跨域要求时，重新评估。
